# GP8 parity W16 and W17: password locks (2026-10-31)

W16 is a password to edit; W17 is a password to open. They are different promises and the interface says so.

## Behavior
- **Password to edit (W16) is a deterrent.** A score has to stay readable to play, so this cannot be encryption. The project keeps a salted Argon2id hash (`editLock`, absent unless set). With it set and not yet given in the session, every edit, undo, redo and backing import is refused with one message; the mixer and master stay usable, as on a finalized score. Giving the password unlocks for the session only (never saved or recovered); a reopened or recovered score is locked again. Anyone who edits the JSON by hand or uses another tool can bypass it, and the dialog and this note say so. A build that predates the field refuses the whole file (`deny_unknown_fields`), so it never opens a locked score and ignores the lock.
- **Password to open (W17) is encryption.** The saved `.tabplayer` becomes `TABPLOCK` + header + XChaCha20-Poly1305 ciphertext of the project JSON, under a key from Argon2id (128 MiB, 3 passes, 1 lane; about 0.2 s here). The header (version, costs, salt, nonce) is authenticated. Without the password the file shows nothing, not even a title. There is no forgotten-password path and the dialog says so.
- **Opening.** A sealed file is checked for structure first, then the app asks for the password in a dialog. A wrong password, a changed file and a cut-short body all give the same message ("The password is incorrect, or this file is damaged."), the dialog stays, the field clears and takes focus, and the file keeps waiting (at most four wait). Cancel stops it waiting. The key is kept in memory so Save needs no password; the password is not. Save and Save As stay sealed.
- **Changes.** Set, change and remove are done in a Password protection dialog (File menu); changing or removing needs the current password. They are not edits (no undo step: undoing a removal would otherwise bypass the password) and make the document unsaved. Unlock editing is also offered from a banner.
- **What a sealed score does not do.** No recovery backup is written for it (its slot is kept, blank, so the backup holds nothing of it), and when a score becomes sealed the older backup that still holds it is dropped with that checkpoint (`commit_keeping`). Saving a sealed score asks the recovery worker for that checkpoint at once, so the older plain backup does not wait for the next scheduled one; the request is asynchronous, so a crash in the moment between the save and that write leaves it. It cannot become a template or fork (refused with a reason). The Library catalog is a plain file, so a sealed score sends it no title, artist, album or track names: the frontend sends empty details, and `metadata_ack` checks on the Rust side that the document is sealed, stores nothing and strips any details already stored for that path. Saving a score under a password to open purges its entry from the folder index (`index-<root>.json`) at once, in memory and on disk (`scrub_file`), so a search finds nothing of it before any Refresh; the entry stays listed without details. Details leave memory first, whatever happens to the cache file. A folder publication of unknown outcome is scrubbed too, and its cache rewritten without the details, and reconciling one withholds the details of any file known to be protected, so neither brings them back. The index also remembers which files were sealed during the run, and when a scan publishes it strips details for any of them whose file on disk still begins with the sealed header, so a pass that read the plain file just before it was sealed cannot bring the details back; a file that is plain again is indexed as usual. The folder scan cannot read a sealed file and reports it unreadable. An edit password survives forks, and edit-locked projects are read by the folder scan (`editLock` is checked in `metadata_input.rs` like the other fields).
- **Catalog follows the file on disk.** `metadata_ack` treats a document as sealed when its live password to open is set or when the file it was opened from or last saved to is sealed, so removing the password without saving, then acknowledging, still stores nothing in `catalog.json` and strips what was there.
- **Held back by the edit lock.** While a score is locked for editing, setting, changing or removing its password to open, and finalizing or unfinalizing it, are refused until the password to edit is given.
- **Disclosed.** The dialog says exports are not protected and that a Guitar Pro export opened again has no edit lock; the Export dialog says so for a protected score; a print writes a plain PDF to the app cache for the viewer, which is now removed when TabPlayer starts and when it exits (a viewer that still has it open delays that to the next start).
- **The dialog cannot be closed mid-change** (Done, the close button and Escape refuse while a change runs; they keep focus).
- **Old files.** Projects and recovery checkpoints without the new fields read and write exactly as before.
- **Dependencies (new, need review).** `argon2` 0.5.3 and `chacha20poly1305` 0.10.1 (RustCrypto; the latter had an NCC audit), `zeroize`, `subtle`, `getrandom`. Costs read from a file are bounded (memory 8 KiB to 256 MiB, 1 to 10 passes, 1 to 8 lanes) before any work, and the Argon2 pass runs off the workspace lock.
- **Guitar Pro's own lock.** Not readable or preservable here. The GP8 manual only says that Lock Opening and Lock Editing exist, that the protection is basic, and that a lost open password means the file cannot be opened; it does not describe the format, and alphaTab has no password handling. No protected sample was available, so nothing was tested. TabPlayer's locks apply to `.tabplayer` only; a GP export carries none and the dialog does not imply otherwise.

## Review
First review rejected 84267b0: High, a sealed score's title, artist, album and track names reached the plain `catalog.json`; Medium, the print PDF stayed in the cache and folder scans rejected every edit-locked project; Low, an edit-locked score could be sealed or finalized without its password, the pre-sealing recovery checkpoint stayed on disk, exports were not disclosed as plain, and the dialog could close mid-change. All are fixed in the follow-up commit, each with a test that fails without it (checked by editing each fix out: `metadata_ack` sealed branch, the print cleanup, the `editLock` scan field, the two edit-lock guards, the empty details, the busy close and the blocked section). That claim did not hold for the recovery fix: `keep_previous` was only exercised by a test that calls `commit_keeping` with the flag set by hand, so the wiring in `Inner::flush` had no test (see below).
A second review rejected that for two findings, both fixed in the next commit with tests that fail without the fix (checked by editing each out): sealing in a library folder left the details in `index-<root>.json` until a Refresh, and a password removed but unsaved let details reach `catalog.json` while the file on disk stayed sealed. The reviewer's proof-of-concept tests were not in this worktree, so equivalent tests were written: `sealing_a_score_in_a_library_folder_purges_its_index_entry_at_once_and_later_scans_keep_it_out` and `catalog_details_follow_the_sealed_state_on_disk_not_the_live_password`.
A third review, a security review run after this was merged, rejected it narrowly. Behavior on the main path was correct, but the guards had no test on the real path: removing the `sealed` argument at Save, the `metadata_ack` scrub, the previous-checkpoint rule in flush, or the redaction in flush left every suite green. The same review found that `metadata_ack` scrubbed the index under a raw path while rows hold canonical (`\\?\`) paths on Windows, that the scrub failed silently or without effect while a folder publication was uncertain and that reconciling one could adopt details of a file sealed in the meantime, that the sealed state at Save was read in a second lock and defaulted to plain, that older plain checkpoints stayed until the next flush after a sealed Save, and that the recovery view of a sealed score kept the cursor and track ids. These are fixed in the follow-up commit with the tests above (found after merge, not before it). That follow-up was rejected narrowly by a re-review (no live leak); it asked for tests of the pending-only and opposite scrub branches, of the delete fallback in scrub and reconcile, and of plain-save behavior, a non-timing check at the sealed Save, the selected string and note in the redacted view, and corrections to this note. These are done in a further commit, which passed that review at 16c8513 on Windows.

## Limits
- The edit password is bypassable by design. Nothing checks the mixer exemption against a determined user.
- Passwords cross the webview as JSON strings and are held in ordinary strings by React and serde before they reach Rust, where they are wiped; they cannot be wiped from the webview. The key sits in process memory while a sealed score is open and could be read from a memory dump.
- No password limit on attempts beyond the KDF cost; there is no lockout. No Unicode normalization of passwords, so one typed through a different input method may not match.
- The recovery backup of a sealed score keeps its place, revision and display preferences (zoom, layout) but not its cursor, selected string or note, or track ids. Unsaved work in a sealed score is not recoverable after a crash. A sealed score and its edit history are decrypted whole into memory.
- A sealed file gives the library no title or details; the metadata reader reports it unreadable, and its recent entry keeps only its path and digest.
- If the folder index cannot be rewritten when a score is sealed, its cache file is deleted instead (the details are already gone from memory), so the folder shows no index after a restart until it is refreshed; if the file can be neither rewritten nor deleted the save reports the Library warning and the details stay on disk. Nothing retries that, and saving the same score again does not help: the index in memory no longer holds the details, so that scrub writes and reports nothing. They stay until a Refresh of the folder succeeds or a scrub of another score in it rewrites the cache, and after a restart the score's title is searchable from the cache until then. The details are removed from memory before any file is touched.
- If a scrub cannot rewrite or delete the cache of a folder whose uncertain publication had reached the file, that publication can no longer be reconciled (its bytes no longer match the file). Until TabPlayer restarts, scans of every folder are refused, as are Library Retry, removing a folder and opening a score from any indexed folder; nothing retries it. If the file still holds the previous bytes, it reconciles normally. Either way the details stay on disk as above.
- A score sealed by another build or outside TabPlayer keeps its old entry in the folder index until a Refresh.
- Sealing through one hard link of a file leaves the others plain: the save replaces the file at the path it was given (`write_bytes` writes a new file and renames it), so another name for the same file keeps its earlier plain contents (seen with a hard link in the review's probe; no test is kept), and so does any backup or copy outside TabPlayer. Symlinks are inferred, not run: `atomic-write-file` replaces the link itself and leaves its target untouched, and `write_bytes` does not canonicalize, so saving through a link would be expected to leave the real file plain.
- The recovery diagnostics folder, written only when a startup resolution preserves evidence, is a copy of earlier checkpoints and is not scrubbed: a score that was plain and later sealed can remain in it until it is cleared.
- The print PDF is removed at exit and start, not when the viewer closes, so it lives for the session.
- Not run on macOS or Linux, not driven in the desktop app (port 9223 untouched), and no tab lock icon for a password-locked score.
- Argon2 timing was measured only in this environment's test build (argon2 compiled with optimizations); slower machines will take longer.
