# Hosted instrument: held notes struck again after a seek, a wrap and a range export (2026-11-17)

Follows limit 10 of `2026-11-17-vst-instruments.md`.

**Gap, confirmed in the code.** `Renderer::seek_tick_internal` struck the plan's held notes again on the built-in kit only. A seek flushes the instrument's stream and forgets its held keys, and nothing was sent in their place, so a hit that was sounding at the seek point (or at the start of a range export, which seeks to its first segment) was silent until the next hit. A loop wrap released the instrument's keys and did not strike the ones the plan holds at the loop start.

**Change.** After a seek, a wrap or an export's first seek, the renderer asks for a strike (`restrike_pending`); the first frame rendered at the new position sends it, before that frame's own events: each instrument track gets one NoteOn per key the plan holds, counted under the track's drum map, with the velocity of the last strike. It is the first music frame, not the seek, so a count-in (realtime, between loops, or an export's, all of which run the inserts through `count_in_frame` first) sends nothing and the strike comes with the music. A key is held there iff a NoteOn is before the position and no NoteOff ends it at or before it: the NoteOffs the first frame dispatches (ticks up to the frame's tick plus the 1e-7 the frame's dispatch uses, and before its end tick) are applied first, so a hit that ends exactly where the position begins is not struck only to be released on the same sample, as the built-in kit's strict "ends after the tick" test has it. A key that is held keeps all its overlapping strikes counted, so the plan's NoteOffs leave the right number and end it on the last: one NoteOn and one NoteOff for the key. A wrap releases (`AllNotesOff`) at the wrap and strikes with the first music frame, in that order. An edit hand-over does not strike again: the running instrument keeps its keys and `continue_from` ends the ones the new plan no longer holds. A strike still owed from a seek or wrap before the hand-over (`restrike_pending`) is carried to the renderer that takes over, which sends it on its first music frame under its own plan and map; a drum-map change (`install_mix`) in that window leaves the flag where it is, so the strike is sent under the new map. Both run `retain` on the stage first, and while a strike is owed the stage holds nothing, so `retain` records every key the plan holds as not sent (`short`, the NoteOffs to come for strikes the instrument never got) and the NoteOffs of those keys would be spent against it. The strike therefore takes what it sends out of `short`: `strike_held` lowers it by the strikes it counts, so `held + short` stays the number of NoteOffs the plan still has for the key and the last of them ends the key. A strike that is dropped (no room) leaves `short` alone, so its NoteOffs end nothing, as before. Without that, a key held at the position (a count-in then an edit, or a pause, a drum-map edit and a resume, or a loop whose start is inside a hit) was struck with held = 1 and short = 1, the plan's NoteOff was used up against `short`, and the instrument never got a NoteOff for it until the next wrap, seek, stop or end of the score. A seek or a wrap straight after another one asks again, so the earlier position's strike is never sent. A track a MIDI port plays is not struck, decided when the strike is sent. A NoteOn the block cannot take is counted in `dropped_notes`. Nothing allocates, locks or waits. Files: `audio/renderer.rs`, `audio/plugin_insert.rs`, `audio/dsp.rs`, `tests/audio_plugin_instrument.rs`. No edit type, plan or project field changed, so every recorded edit replays as before.
