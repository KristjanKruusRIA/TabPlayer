# THE-213: Volume and Pan drags, typed frets, track-name clicks (2026-11-14)

Branch `agy/the-213-entry-mix`, cut from `develop` at 77605bb. Everything below was measured on the Windows test build
(`scripts/build-desktop-test.ps1`) with real CDP input (`Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`), on a small score
(3 tracks, 8 bars) and a large one (6 tracks, 200 bars), both generated by alphaTab's own exporter inside the app. Nothing sets a
control's value with a native setter.

## 1. Pan and Volume drags

### Before (develop, 77605bb)

| Surface | What a real drag did |
|---|---|
| Dock rows, Volume (native range) | Sent an edit on every step; the first step made the app busy, the control was `disabled` mid-drag, the drag ended after one step (11 moves, 1 edit, value one step from the start). Owner/orchestrator measurement. |
| Dock rows, Pan knob | Sent edits from `onInput` as well as `onCommit`; disabled mid-drag the same way; no `pointerup` reached it. Owner/orchestrator measurement. |
| Mixer view fader (`.mixer-strip-fader`), small score | Press on the track jumped the thumb, then `lostpointercapture` arrived 44 ms later and the gesture was cancelled: 0 edits, value unchanged. |
| Mixer view pan knob (`.mixer-strip-pan`), small score | 7 of 12 moves reached the knob, no `pointerup` ever did; the draft stopped at 0.25 and nothing was committed: 0 edits. |

### Why the Mixer view failed (evidence)

Not busy: in the Mixer view runs there were no `aria-busy` toggles and no `disabled` mutations on the dragged control. The cause is
pointer capture. `setPointerCapture` succeeded on the press (`hasPointerCapture` true), but by the first following move it was
false, with no `gotpointercapture`/`lostpointercapture` for the knob; the `pointerup` then went to whatever was under the pointer
(`doc-pointerup` target `mixer-strip-switches`). The same happens to a plain `<div>` injected into the page (capture true at press,
false at the first move), so it is the webview given mouse events from outside, not the Mixer view's markup. `Knob` and `Fader`
(`useRange`) listened for `pointermove`/`pointerup` only on the control and treated `lostpointercapture` as the end of the gesture,
so they depended on capture that was gone. Note that the orchestrator's earlier "Mixer view" numbers came from the **dock's Mixer
mode** (`.track-mixer`, native ranges, reached through "Dock views > Mixer"), which is a different component from `MixerView`; that one
failed for the busy/`disabled` reason above.

Not established: whether a physical mouse in the installed WebView2 also loses capture. The fix does not depend on the answer.

### What changed

- `src/ui/useRange.ts`: a pointer gesture is followed on the `window` (move, up, cancel) from the press, so it no longer needs capture;
  `lostpointercapture` no longer ends it (a move with no button held still does); new `busy` option refuses a gesture that has not begun
  (press, keys, wheel, double-click, typing) but never cancels one under way; `disabled` still ends a drag.
- `src/ui/Knob.tsx`, `src/ui/Fader.tsx`: `busy` prop (`aria-disabled` and dimmed, still focusable).
- `src/ui/MixSlider.tsx` (new): the dock's horizontal Volume range and the dock Mixer mode's ranges. A native range with `Knob`/`Fader`'s
  contract (`onInput` while moving, one `onCommit` at the release or at a key's release, nothing when it ends where it began, Escape
  cancels). A mouse drag is followed on the window, because a native range stops following after the first move without capture. Never
  sets `disabled` for busy.
- `src/TrackPanel.tsx`: dock rows and the dock Mixer mode use `MixSlider`/`Knob` with `busy`, hear the drag through `previewMix` (as the Mixer
  view does), record one `setTrackMix` at the end; `Knob` no longer calls `setPan` from `onInput`.
- `src/mixer/MixerView.tsx`: faders, pans, drum-kit controls and the Focus knob pass `busy` instead of `disabled`.
- Tests: `src/ui/busy-drag.test.tsx` (new), `src/ui/gesture.test.tsx`, `src/TrackPanel.dock.test.tsx`, `src/TrackPanel.test.tsx`,
  `src/mixer/MixerView.test.tsx`. Two older tests that required "busy ends the drag" and "lost capture ends the drag" were replaced
  with the new rule.

### After (this branch), `tests/desktop/parity-mix-drag.mjs small|large`

Both sizes pass every assertion: one `setTrackMix` per drag; the final value within tolerance of the pointer; the release reached the
window; the dragged control never had a `disabled` attribute change; a drag that returns to its start records nothing; one arrow
step on the dock Volume and one on the dock Pan are one edit each. Surfaces: dock Volume, dock Pan, dock Mixer-mode Volume and Pan,
Mixer view fader and pan. The app went busy for the commit only (`aria-busy` true then false once), never during the drag.

## 2. Typing fret numbers

Decision (owner, 2026-11-14): a typed digit writes the note at once, as in Guitar Pro.

- A digit writes that fret on the cursor's string immediately (`setNote`, with the automatic duration as the existing `sequence` pair
  when that is on). No Enter. The cursor does not move, in or out of note entry, as before.
- Window: **1000 ms** between two digits (the existing digit window; Guitar Pro's is about the same). A second digit inside it makes
  the two-digit fret when `applyInOrder` accepts it for the track (1 then 2 = 12); otherwise it is a new single-digit fret on the same
  string (9 then 9: the second 9 is fret 9 again and records nothing, since the note already has it).
- One undo step without a new edit type: the first digit's edit is **undone and the two-digit fret written in its place**
  (`controller.undo()` then `controller.edit(setNote)`), after checking that nothing changed in between (same document revision, same
  beat and string, within the window). One undo then restores what stood before the first digit, and the history holds one edit. Cost:
  the second digit does an undo and an edit, so two rebuilds instead of one. Old projects and logs replay unchanged; no edit type or
  schema change.
- Keys typed while an earlier edit is still applying wait in the existing queue and run in order against the cursor as it stands; the
  per-key age rule, the "queued keys were dropped" notice and the rule that a second digit is dropped with its stale first digit are
  unchanged. Held-key repeats of a digit are ignored. A digit while playback is running with "write while playing" off is refused with
  the existing paused notice.
- Enter: no longer needed. It still writes the Fret field's value on the cursor string (for a fret set from the field or the instrument
  view) and records nothing when the note already has that fret, so the old "digits, Enter" habit adds nothing. It also ends the window.
- Escape: ends the wait for a second digit (the hint goes; the next digit is a new fret) and takes nothing back; Undo removes a written note.
- Backspace: removes the note on the string, as for any note (it no longer "takes back typed digits", since they are written).
- Texts (en, et, de): the status/hint line is now "Fret N written: another digit within a second makes it two digits"; the shortcut
  tables, the Score help line and the Editing help topic say the same; `status.hint_score` and `keys.digits_enter` no longer mention Enter.
- Code: `src/App.tsx` only in the entry/key code (`fretPlan`, `writeFret`, `enterFret`, `typeFretDigit`, `fretRun`, the place-key effect,
  Escape/Backspace branches, `writesNote`, the repeat guard). Tests: `src/App.test.tsx` (new digit tests; the pending-fret, Escape and
  Enter tests were rewritten to the new rules).

### Measured, `tests/desktop/parity-fret-typing.mjs small|large` (real click on a fret number, real keys)

Both sizes pass: `5` adds one edit at once and the position text does not change; Enter after it adds none; `1`,`2` 120 ms apart adds one
edit, fret 12, and one Ctrl+Z returns the edit count to what it was; `9`,`9` ends as fret 9; `1`, 1.5 s, `2` is two edits (1, then 2);
`1`,`2` 30 ms apart on a new beat is one edit, fret 12.

## 3. Track names

Found: in the dock the name is a plain `<span>` in the row header (no handler, so a click did nothing; only the bar cells selected);
in the Mixer view it is a button, but it went through `busyGuard`, so while busy it was refused, and in the dock's Mixer mode it was
`disabled` while busy. Neither used a rename, so none was displaced (rename stays in the inspector's track settings). The Mixer view
also moved the cursor to beat 0.

Now: `src/workstation/ScoreOverview.tsx` renders the name as a button (`Select track NAME`, `aria-pressed` for the active one) in the dock
rows; the Mixer strip and Mixer-mode channel buttons are no longer refused for busy. `App.selectTrack` moves the cursor to the same bar and
beat (clamped by `repairSelection`) and string where the track has it; after a pointer click it hands the keys to the score pane. It is
navigation: nothing is recorded and the document does not become dirty. Keyboard: the buttons are focusable, Enter and Space work
(the grid's cell keys are stopped on the name button). Text key `overview.select_track` in en, et ("Vali rada {track}") and de.

Measured, `tests/desktop/parity-track-click.mjs small|large` (real click on each name, then a digit): in the dock and in the Mixer view
each click makes the name pressed, the edit count and the dirty flag do not change, and the digit lands on the chosen track. In the Mixer
view there is no score to type on, so the driver returns to the Score view (focusing the workspace with a script call, not a click)
before typing.

## Limits

- Pointer capture loss was shown for CDP-injected mouse events. It was not shown for a physical mouse.
- The audible preview was not listened to; the drags call `previewMix` (`audio_set_mix` IPC), as the Mixer view always did.
- The Mixer view's keyboard-typed fret after a track click was checked by returning to the Score view, not inside the Mixer view.
- macOS and Linux were not run. Touch and pen use the native range path of `MixSlider`.
- The two-digit join does an undo and an edit; its cost on a very large score was not measured separately from the single edit.

## Review fixes (second pass)

1. `MixSlider` ignores key releases and key presses (except Escape) while a mouse drag is under way; Shift or Ctrl released mid-drag no longer
   commits it, arrow keys no longer move the range under the pointer. Driver: a real Shift press and release halfway through a drag is still one edit.
2. `MixSlider` drags relative to where the thumb was grabbed (a press within the thumb, with 6 px of slop, changes nothing until the pointer moves);
   a press on the bare track jumps there. The thumb's width comes from `--mix-thumb` (7 px for the dock Volume, 16 px otherwise).
   Verified with real mouse clicks at the thumb's centre and 3 px either side, at the maximum and after a drag: no edit. A click 6 px right of the
   centre at value 0.3 did record one step (0.35) in a probe; the slop is a few pixels, not a guarantee up to the edge.
3. The grid's key handler ignores events from buttons inside it, so the track-name button no longer swallows keys: Ctrl+Z, Ctrl+S reach the app after
   Enter or Space on a name; Enter and Space still press it.
4. Two-digit join, failure paths: the join now needs the first digit's edit to be the last edit (same revision, same edit count, same command), no pending
   controller action, and the same place. After the undo it checks again that the edit undone was that one. A failure after the undo (no beat, refused write,
   a different edit was undone, a thrown error) does a Redo and says "The first digit was put back."; a Redo that fails says so
   ("could not be put back") and is logged, never swallowed.
   - Note already had the two digits (note 12, type 1 then 2): the document ends as it was before the first digit and one edit is in the history for the
     whole thing (none). What remains: the undone "1" stays in the Redo stack, so Redo would write fret 1. The history has no way to drop a redo entry
     without a new edit or a format change, so this is left and documented here; a test pins it.
   - Cost, measured with real keys on the test build (IPC counts per step): a single digit is 1 `apply_edit`; a two-digit join is `apply_edit` + `undo_edit`
     + `apply_edit` (three document changes, each followed by the audio rebuild). The note shows 1, then the original, then 12, so there is a flicker.
     Busy time (key press to the last busy end, other agents were using the machine): small score 0.4 s single, 1.2 s and 0.35 s for two joins; large
     score (6 tracks, 200 bars) 0.78 s single digit and 3.0 s and 4.3 s for the two joins. Fewer rebuilds or no flicker would need an edit that replaces
     a previous edit, which is a new edit type or a history change, so it was not done.
5. Dock mix gestures find their track by identity at preview and at commit, and the dock controls are keyed by track identity, so a track list that
   changes mid-drag (Ctrl+Z, a deletion) ends the drag without an edit instead of saving onto the track that took its place. Tests for the volume range and the pan knob.
6. `MixSlider` ends a drag without an edit and takes the preview back when the window loses focus, a press lands elsewhere or the pointer is cancelled;
   Escape during a drag is consumed (it does not reach the app's Escape handler).
7. A digit that cannot write says why: no strings on the staff (new text in en, et, de), no beat (the existing "Select a beat with room for a note"), and a
   refused write ("Fret 7 was not entered: the edit was refused"). Digits are now entry items on percussion and notation-only staves too, so they can say it.
8. Zero: a leading zero never joins. 0 then 5 is a fret 0 and then a fret 5 (two edits), 0 then 1 is 0 then 1; "0,1,2" is 0, then 1, then 12 (the 1 and 2 join,
   not a collapsed 01). Tests and a driver step.
9. `help-et.ts` now says „Võta tagasi“; `keys.digits_enter` is renamed `keys.digits`.
10. Tests added: App-level `selectTrack` (same bar and beat, nothing recorded, not dirty); refused write after the undo; an outside edit between the digits;
    digits with Ctrl/Alt/Meta; key release mid-drag; click on the thumb; Escape consumed; blur, press elsewhere and pointer cancel; dock tracks changing mid-drag;
    name button keys.
