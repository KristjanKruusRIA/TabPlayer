# GP8 Fretlight guitar lights (THE-77, tracker row U19)

Date: 2026-11-14. Branch `agy/the-77-fretlight`, uncommitted at the time of writing. Design and protocol research: `docs/superpowers/specs/2026-11-14-mysongbook-fretlight-design.md` (Part 2). Owner decisions of 2026-11-14: build the device-independent half and the wired USB transport, ship it labelled "untested on hardware", leave wireless models out, add `hidapi` as the one new dependency, and implement from the documented layout without copying any other project's code.

## Scope

A View-menu section "Fretlight guitar" connects to a wired Fretlight guitar and lights the notes of the selected track on its neck, following the instrument view's Show choice (Playing notes, Selected beat, Selected bar, Next beat). **No real Fretlight was ever connected to this code.** Everything below that says "passed" was run against a fake USB stack or a fake device, never against hardware.

## What was built

- `src-tauri/src/fretlight.rs`: the frame type (132 LEDs, six strings by frets 0 to 21), the encoder to the three 7-byte packets, a `HidBackend` trait with a `hidapi` backend (started on the first listing, which only Connect asks for) and a fake backend, the session state machine (disconnected, connecting, connected, lost, error), a worker thread that owns the device and takes frames from a one-slot latest-wins mailbox, the commands `fretlight_connect`, `fretlight_frame`, `fretlight_disconnect`, `fretlight_status`, the `fretlight-status` event, and the desktop-test-only `fretlight_test_log`. Registered in both invoke handler lists; the exit handler writes the all-off frame first.
- `src/fretlight/frame.ts` (the frame model), `fretlight-session.ts` (the page's session store), `FretlightFeed.tsx` (computes the lit set and hands it to the session), `FretlightPanel.tsx` and its CSS; `src/instruments/fret-positions.ts` (the note-to-string-and-fret step, extracted from `InstrumentView.tsx` so the view and the lights read the same positions), `use-focused-notes.ts` (the shown notes, extracted from `LiveInstrumentView.tsx`, so the lights do not need the view on screen), `use-instrument-focus.ts`.
- `fretlight.*` text in en, et and de, and the help section "Fretlight guitar lights" under Instrument views (`help.topic.instruments.fretlight.*`, reached from the section by context help).
- `tests/desktop/parity-fretlight.mjs`.

## Protocol source and confidence

One community blog post (Rick Regan, Exploring Binary), who says he captured the USB traffic of Guitar Pro 6 and that it matched two open-source projects. Nothing was copied from those projects or read from their source; the layout was implemented from the design note's summary: USB HID, vendor id 0x0925, product id 0x2000; the host writes one 8-byte report (report id 0, then 7 bytes) per packet; packet bytes 0 to 5 are LED bits and byte 6 is the packet number 1, 2 or 3, covering frets 0 to 7, 8 to 15 and 16 to 21; strings are numbered 1 to 6 from the high E; with `k = (fret - first fret of the packet) * 6 + (string - 1)`, LED `k` is bit `7 - k mod 8` of byte `5 - k / 8`. Confidence: medium at best (one author, one guitar of unknown model, a secondary description of USB traffic).

**Checked against the source's own tables (review item, 2026-11-14).** The post was fetched again as HTML and its three tables (section "The Fretlight Interface": "Packet ID 1", "Packet ID 2", "Packet ID 3") were copied cell for cell into `SOURCE_TABLES` in `fretlight.rs`. Tests assert that each of the 132 named cells (`fFsS`: fret F on string S, string 1 the high E) lights exactly that byte and bit and nothing else, that the cells the post marks `xxxxx` are never set, and that `f21s6`, `f21s1`, `f18s1` and `f19s5`, which the post names among the 19 LEDs of its clock, sit where its Packet ID 3 table puts them. The tables agree with the formula, cell for cell, so the formula was an accurate summary and a mirrored string or bit order would now fail. The post prints no example packet bytes: the only hex values are the packet ids (0x01, 0x02, 0x03) and the vendor and product ids. It says each report is 8 bytes (report id 0 and the 7-byte packet), and that its clock sends only packet ID 3 once a second; that hints the packets are independent but does not say whether lit LEDs persist, so every update here still sends all three packets. This checks the code against the source; it does not check the source against a guitar. The post does not say how LEDs clear, whether they persist without refreshing, what the device reports as its product name, or anything about timing or brightness.

## Decisions where the design was silent

- **Clearing.** Every update writes all three packets with the full state; all-off clears. Disconnect and exit write an all-off frame first, waiting at most 1.5 s for it. After a failed write nothing more is written and the LEDs stay as they are.
- **Rate.** At most 25 frames a second reach the device (`FRAMES_PER_SECOND`), enforced by the worker whatever the page sends; the page also keeps one send in flight and sends only the newest frame after it. The mailbox holds one frame, so there is no queue. The first frame after a quiet moment is written at once.
- **Device match.** Vendor id and product id and a product name containing "fretlight" (any case), because the vendor id may be shared. The real product name is not documented; if a guitar reports another name it will not be found, which fails safe.
- **Which tracks.** Only a pitched staff with exactly six strings is sent, whatever its tuning or instrument; any other track (percussion, keyboard, four-string bass, seven strings and more, a banjo) lights nothing and the section says so. A six-string bass would be sent: the rule is the string count, not the sound.
- **Tuning.** Ignored. Tuning changes pitch, not where a finger goes, so a drop D neck lights the same frets.
- **Capo.** The physical fret is lit: the written number plus the capo on that string, including a partial capo (`ledFret` in `frame.ts`, a single tested function with a `written` mode to flip it). The instrument view shows the written number counted from the capo. Nobody has checked which a real guitar should show.
- **Left-handed view.** Does not mirror the lights: the device is a physical neck and its LED map is fixed.
- **A device with the ids and another name** is never opened, but its name (up to three, at most 40 characters each, control characters and `|` removed) is carried in the Connect error and shown in the section: "A device with the Fretlight USB ids was found but is named ...; it was not opened." A tester whose guitar reports another name can say what it is.
- **A worker that ends for any reason** (a write that fails, or a panic inside a driver) leaves the session lost with a notice, and `send_frame` then fails; a panic is caught by a drop guard at the worker boundary. The wait for the next frame reads the clock once and uses a saturating subtraction (the first version read it twice and could panic if the interval ended between the reads).
- **A write that never returns.** Disconnect and exit wait at most 1.5 s for the all-off frame. A worker that has not ended by then is remembered, and Connect is refused ("worker_stuck") until it has, so two workers never share the device. A worker whose session was replaced by a newer one skips its all-off frame, so it cannot blank the newer lights.
- **Above fret 21.** Dropped and counted; the section says how many.
- **Held (tied) notes** are lit as the view marks them. Percussion and non-tab staves send an empty frame.
- **Which view the lights follow.** The instrument view's Show choice. The section has the same choice, written to the same setting, so changing it in either place changes both; it works while the instrument view is closed.
- **Scale mode: not done.** Scale overlays exist only inside the Scale browser dialog, whose root, pattern and positions are local component state. Sending them to the lights needs that state lifted into the app, which is not a small addition on top of the frame model, so it is left out. The tracker's "score/scale modes" is therefore only met for the score modes.

## Dependency

`hidapi` 2.6.7 (crates.io, released 2026-08-27), MIT, pinned with `=`, with `default-features = false, features = ["windows-native", "linux-native-basic-udev"]`. Both are pure-Rust backends: on Windows and Linux no C library is compiled and no system package is needed (the Linux backend reads the udev database itself through `basic-udev` 0.1.3, MIT OR Apache-2.0, and `nix` 0.30.1, MIT). `basic-udev` ships no licence file and states no copyright holder, so its MIT text is kept as `legal/basic-udev-MIT.txt` ("Copyright the basic-udev authors", as the repository does for other crates without one) and copied by an explicit step in `scripts/copy-notices.mjs`. macOS builds the HIDAPI C library bundled in the crate, used under its BSD-style licence (`legal/hidapi-bsd-license.txt`, copied the same way), and links the IOKit, CoreFoundation and AppKit frameworks, which are part of the system. **Enumeration:** hidapi 2.6.7's `HidApi::new()` walks the system's HID devices once whatever the discovery setting says (`new_without_enumerate` only affects the libusb backend), so Connect cannot avoid that one walk; the backend drops everything but the Fretlight ids at once (`reset_devices`, then `add_devices` for the id pair) and refreshes with those ids alone, and nothing else is read, kept or reported. `THIRD_PARTY_NOTICES.md` has the entry. CI (`.github/workflows/desktop.yml`) installs no libudev or libusb packages and needs none with these features. **Not verified:** the Linux and macOS builds were never compiled here (only the Windows target is installed). On Linux a user also needs permission to open the hidraw device (a udev rule); that is not handled or documented in the app.

The driver does not exercise `hidapi`, a real USB stack or unplugging, and does not drive repeats or loops.

## Not verified

- **No real Fretlight was ever connected.** Nothing here shows that a guitar lights the right LED, or any LED. The `hidapi` backend (listing, opening by path, writing the 8-byte report) was never run against a device or a real USB stack.
- Whether the LEDs persist without refreshing is unknown. They are written on a change only, so a guitar that needs refreshing would go dark.
- The product name a real guitar reports is unknown; the match on "fretlight" is a guess.
- Whether the capo should show the physical or the written fret is unverified.
- The documented layout comes from one community source; whether all wired models use 22 frets is unknown.
- Wireless models are not supported and their protocol is not public.
- macOS and Linux were not built or run; the Linux hidraw permission rule is not handled.
- An unplugged guitar is noticed at the next write, not at once: nothing polls the device while no frame is sent.
- **Scale mode is not built.** The tracker row asks for score and scale modes; only the four score modes are met, which is one of the reasons the row stays partial.
- The Estonian and German text was written by the assistant and has not been reviewed by a speaker.
- Latency: the lit state travels native playback state to the page and back to a native command; the delay was not measured.
