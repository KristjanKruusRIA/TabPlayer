# F08: batch legacy GP converter

Date: 2026-10-24. Status: design. Row F08 ("Batch legacy GP converter") stays at its current status until the source review, the security review of the new file access, the automated checks and one desktop run pass.

## Brief

GP8's batch converter turns a folder of older Guitar Pro files into the current format in one go. TabPlayer converts one score at a time, by opening and exporting it. This slice adds **File > Batch convert…**: pick a source folder, the file types and a destination folder, and every matching score under the source, in its subfolders too, is written as a new `.gp` file, with a result for each file. It reuses the import and export code that opening and exporting use (`loadInterchangeScore`, `exportGpInterchange`) and adds no edit command, so the protocol does not change.

## Behaviour

- **The dialog** (`src/batch/BatchConvertDialog.tsx`, modal like the ASCII import) has:
  - **Choose source folder…** and **Choose destination folder…**, each showing the picked path;
  - **File types**: Guitar Pro 3, 4 and 5; Guitar Pro 6 (`.gpx`); Guitar Pro 7 and 8 (`.gp`, written again in the current format); MusicXML (`.xml .musicxml .mxl`). The two legacy Guitar Pro types are on by default, the others off;
  - **Keep the subfolders in the destination** (on by default; off puts every result directly in the destination);
  - **Convert**, enabled with both folders, at least one type and no document operation under way; **Cancel conversion** while a run is under way; **Close**.
- **A run** first scans, then handles the files one at a time. It yields to the UI between files, so progress ("Converting 3 of 12…") and Cancel stay live. Each file is read natively and **probed first in a Worker** (`src/batch/probe.ts`: the stock importer, a 32 MiB decoding cap and a 15 second deadline, `terminate()` on expiry), because a damaged `.gpx` can make the importer spin forever or allocate without end. Only a file that passes is imported, exported to the current GP format, read back and compared (track and bar counts) on the window thread, then written. A file counts as converted only after its output was written. A file the probe times out on is reported Failed and the run goes on. The probe is a reusable helper (`probeScoreBytes`); single-file Open, which has the same hang, is not changed here. The probe message carries a `cmd` of its own (`tabplayer.batch.probe`), because alphaTab registers its own message listeners in any Worker and reads `cmd` from every message; one without it throws and fails every file. Cancel also ends a check under way, and the file is then reported as Not converted, not Failed.
- **Failure isolation:** a file that cannot be read, imported, exported or written is reported as Failed with the reason, and the next file follows.
- **The report** is a table with one row per file: relative path, result (Converted, Failed, Skipped, Not converted) and detail (track and bar counts and the name it was saved as, or the reason). A summary line reads "12 converted, 1 failed, 1 skipped." Files never listed are those of other types.
- **Cancel** (button or Escape) takes effect before the next file; the file under way finishes. Files not reached are listed as Not converted. Close is disabled during a run; Escape then cancels instead of closing. Closing the dialog tells the native side to forget the folders and the scan (`batch_reset`).
- **Output names:** `<name>.gp` in the matching subfolder. A taken name never gets replaced: the result is `<name> (2).gp`, `(3)` and so on up to 99, and the report says it was saved under another name because the name was taken. Two sources with the same stem in one folder (`a.gp3`, `a.gp5`) therefore both survive.
- **The open document is untouched.** The dialog never calls `edit()`, opens a document or changes selection. The File menu button is disabled while documents are busy.

## Native side (security review needed)

New file access: `src-tauri/src/batch_convert.rs`, four commands (`batch_pick_folder`, `batch_scan`, `batch_read`, `batch_write`) and managed `BatchState`. `capabilities/default.json` does not change: the folder dialog is called from Rust, as `export_track_files` and the Library already do. Small visibility changes in `intake.rs` (`read_stable`, `component_prefix`, `reparse` become `pub(crate)`) so the existing stable-read and link checks are reused.

- **The window never names a path.** Folders are picked by the native dialog and kept in `BatchState`; files are addressed by index in the last scan. `batch_write` receives an index and bytes, nothing else.
- **Reading:**
  - confined to the source through `read_stable` with the source as scope: no link or reparse point in the path, a file that changes during the read is refused;
  - files are never opened for writing;
  - the scan does not follow links or junctions (reported as skipped).
- **Separation:** the destination may not be the source, inside it, or contain it. Decided by **file identity** (volume and file index through `GetFileInformationByHandle`, in `src-tauri/src/fs_identity.rs`) while walking up the ancestors of each folder, never by comparing names, so the administrative-share spellings of the source (localhost, 127.0.0.1, the computer's own name, and their extended UNC forms) count as the source. If an identity cannot be read the pick is refused. Checked on picking either folder and again at every write. `file_library/protected.rs` uses the same identity check against the protected roots, in addition to its name comparison. A destination whose attributes cannot be read is refused here (strictly fail-closed); in `protected.rs` only an access-denied answer from a folder above the target counts as no match (the name checks still apply), because Save and Export must not break on a folder whose attributes the user cannot read. Any other identity error still refuses there.
- **Writing:**
  - **Folders:** the destination and every folder below it are **opened as themselves and held open for the whole write**: `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`, real access 0x81 (list and read attributes; attribute-only access skips the share checks), sharing read and write but not delete. A link is refused where it is opened, not followed, and while the handles are held none of the folders can be renamed, deleted or replaced. A folder is passed to `NativeAudio::protect_destination` before it is created or entered. The finished folder must still lie under the destination and not under the source. This replaced a path-based check that a swap between the check and the use could beat (387 files landed outside in 60 s in the reviewer's race; 0 in the same race now). On other systems folders cannot be held, so the same checks on where the file landed detect a swap and delete the file; they do not prevent it.
  - **Files:** the bytes are written to a temporary name in that folder (`.tabplayer-batch-<pid>-<n>.tmp`) whose handle stays open through the rename. The handle's final path is checked by identity, before and after the rename: its folder must be the one held, below the destination and never in or below the source, or the file is deleted and the write fails. The rename does not replace (`MoveFileExW` with no replace flag, retried briefly on a sharing violation; elsewhere a hard link, or a `create_new` copy where hard links are unavailable), so nothing is ever replaced and a killed run leaves no truncated `.gp`. Every failure path removes the temporary file, and the first write into a folder sweeps `.tabplayer-batch-*.tmp` files untouched for an hour (an interrupted earlier run's).
  - **Content and totals:** the output must start with the ZIP signature and be at most 64 MiB; each file of a scan can be written once (indices start again with each scan); a session writes at most 512 MiB in total, counted across scans until a destination is chosen again or the dialog closes.
  - **Destination choice:** protection is asked before the destination is kept, so a refused folder leaves the earlier choice. Choosing a destination, like a new scan, starts a new run and clears the list of files.
  - **Names:** a name from a listing must be one plain component (no separators or control characters); on Windows also no colon and no trailing dot or space. Others are reported as skipped. Windows device names (`Con.gp5`, `Aux. Pt 2.gp5`, a folder `Aux`) are legal in the extended path form these operations use, so they are converted, and the report adds a note that other Windows programs may read the name as a device. Numbered copies run `(2)` to `(99)`; past that the file fails with a message saying so.
  - **Picker:** parented to the main window; Close and Escape are inactive while it is open.
- **Bounds:** 500 files, 32 MiB per file, 512 MiB in total, folders up to 12 levels deep, 20,000 directory entries examined (counted while listing, so a huge folder is never held whole), 1,000 skipped rows. A listing that fails ends that folder with a skipped row and is not read again. Past a limit the scan stops and the summary says the folder holds more than one run can convert and to **choose a subfolder, or fewer file types**, because a rerun would redo the same first files. The same note shows when nothing was listed. Links are reported as skipped only if they could have been scores or folders, and an entry that cannot be inspected gets a row instead of vanishing. A share path shows as `\\server\share`.
- **The converted bytes** travel to `batch_write` as the raw request body (index and folder option in headers), not as a number array.
- **Desktop-test builds** answer the pickers from `TABPLAYER_TEST_BATCH_SOURCE` and `TABPLAYER_TEST_BATCH_DESTINATION`, as `export_folder` does with `TABPLAYER_TEST_EXPORT_DIR`.
- The commands check the same workspace admission as the Library, so nothing runs during a session transition.

## Acceptance

- **Rust tests:** scan filters, recursion and order; limits (file count, file size, depth); destination separation in both directions and for a junction; reads confined to the scan and originals unchanged; new-file-only writes with kept or flat folders, numbered names, case-insensitive clashes, refused bytes, protected places and a vanished destination. Also: the pin and identity helpers (`fs_identity.rs`), a swap that the held handles refuse, junctions at a folder that does not exist yet, stale temporary files, device names, and `protected.rs` with a loopback spelling and with a folder whose attributes are denied by ACL.
- **TypeScript tests:** conversion of generated MusicXML and, where `.analysis/compatibility` exists (or `TABPLAYER_COMPATIBILITY_DIR` names it), of the public GP3, GP4, GP5, GP6 and GP7 files, with their notes equal after the round trip; failure isolation, cancel, the report and the summary; the dialog's states. `probe.test.ts` runs the real `probe.worker.ts` module on a Node thread that behaves like a Worker for what alphaTab looks at (`WorkerGlobalScope` present, its own message listeners, a throwing listener reported as an error): it proves the module loads and answers with alphaTab's listeners present, that a request without `cmd` throws as it did in the webview, that the public fixtures and generated MusicXML pass and bad bytes fail, and that the saved hanging GPX is cut off by the deadline. It cannot prove bundling of the Worker URL, module-Worker, transfer or error-event behaviour in the webview; the desktop driver does, because with a broken Worker every file fails. `src/interchange/zip-limits.test.ts` covers the archive total.
- **Desktop** (`tests/desktop/parity-batch-convert.mjs`, on a Windows desktop-test build): a nested mixed corpus (legacy files in subfolders, a current `.gp` and a MusicXML file that are not chosen, a broken file and a text file) is converted with the default types; the report lists exactly the chosen types with the broken file failed; the outputs are new `.gp` files in the kept folders that load; the source tree is byte-identical; a second run writes numbered copies and replaces nothing; Escape cancels with a report that matches the disk; the open score and tabs are unchanged.

## Archive total

One validator, `src/interchange/archive.ts`, runs in a Worker under the 15 s deadline before any parser sees the bytes, on batch and on single-file Open. It works from the real bytes: the entry count (4096), entries that are contiguous, fit in the file and agree between local headers and central directory, Zip64 fields that match the archive exactly, stored sizes that are equal, and output measured by inflating with fflate's streaming `Inflate`, which stops at the limit on bytes actually produced. An archive that disagrees with itself is refused, because alphaTab walks local headers while fflate follows the central directory. Batch allows 32 MiB per entry and 64 MiB in total. Open allows 128 MB per entry and 256 MB in total, so a score with a large backing track still opens. The window parsers call `assertArchiveAccepted`, so bytes that skipped a Worker are validated there before fflate or alphaTab reads them.

The validator does not check CRCs, and it inflates with fflate where alphaTab uses its own decoder, so the two could still differ on a stream only one of them accepts.

## Recorded limits

- The probe costs up to 15 s per file before it gives up. A file that passes it can still freeze the window, because reading, writing and reading back run on the window thread. Measured in headless Edge: 2.9 s and 1.3 GiB for 5 MiB of MusicXML, 5.9 s and 2.5 GiB for 12 MiB, 25.5 s and 3.8 GiB for 20 MiB (41,467 bars). At 26 and 31.5 MiB the file fails after about 7 s and up to 4.6 GiB, because the written `score.gpif` passes the 128 MB entry limit that writing and reading back are held to. The earlier 13 s figure was too low.
- An Open of a truthful archive at the limit (240 MiB of zeros) took 1.8 s on the window and 796 MiB. That stream is the cheapest to inflate, so it is not an upper bound.
- Open decodes the project's base64 on the window before the Worker sees the bytes: a 31 MB crafted file was refused after 1.3 s, with 844 MiB peak including the harness's own copy.
- On Linux and macOS each write goes through a held directory descriptor (`openat`, `linkat`, `unlinkat`), but the folders themselves are still opened by path. This code has not been compiled or run on those systems.
- Separation and protection compare identities by opening every ancestor, which costs a little per check and is slow on network shares.
- A network share whose root is a folder inside the source is a known gap (reviewer item N11): separation walks the ancestors of each chosen path, and a path reached through such a share starts at the share root, so what lies above the root inside the source is not seen. It is recorded, not closed.
- Another running copy of the application can be writing a temporary file when it is old enough to be swept (an hour); the sweep leaves anything newer alone.

## Scope

- No MIDI or ASCII tab input, no option to convert in place or to overwrite, and no skip-existing mode.
- No saved report file and no per-file conversion settings.
- Conversion runs on the window's thread, one file at a time; a worker is a later change if very large folders prove slow.
- Files the importer accepts but renders imperfectly are reported as converted: the check is that the result reads back with the same tracks and bars, not a musical comparison.
