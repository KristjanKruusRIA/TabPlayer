# Guitar Pro 8 Harmony Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver structured chord/scale tools and atomic chromatic/diatonic transposition with persistent native definitions and a personal library.

**Architecture:** Root stages exact types and a narrow atomic pitch-target helper. Independent workers own pure chord/scale theory, owned chord/source adapters, transpose preparation and library modules; root joins existing score/history/clipboard/export/UI paths and verifies them on desktop.

**Tech Stack:** Existing alphaTab1.8.4, TypeScript/React, Rust1.88/Tauri and Vitest; no product dependencies or live-audio architecture changes.

**Spec:** [2026-10-15-gp8-harmony-design.md](../specs/2026-10-15-gp8-harmony-design.md)

## Global Constraints

- Native projects remain schema version **2**, engine version **1.8.4**, immutable source plus finite commands. Existing command histories retain their meaning.
- Use alphaTab **1.8.4**, fflate **0.8.3** and the existing Rust/Tauri/React stack; no new product dependencies or proprietary catalogs/assets.
- Root owns shared DTOs, validators, engine/range helpers, App/EditorPanel/ScoreView, playback/export/clipboard integration, Git, builds/apps and native verification. Workers own isolated new modules/tests only.
- Validate all notes/chords/key destinations before mutation; each document edit is one history entry. Browse/recognize/library management does not dirty the score.
- Preserve per-note dynamics, valid links, raw lyric sources, backing bytes/anchors, GP archive siblings, settings replay and unselected music through every clone/rebuild/export.
- Standard GPIF output uses demonstrated public/native fields only. Native metadata retention, public GP roundtrip, actual MIDI/audio and original-GP8 acceptance are separate claims.
- Keep the approved slate/cream/lime layout, note-name pitch displays and one-based user labels. Unsupported musical/contextual inputs reject visibly rather than losing data.

## Review Focus

1. Different diatonic note deltas can collide if applied sequentially; Task1/4 test one atomic proposal set, an invalid last target, unequal internal ties and duplicate incoming ties with surviving canonical edges.
2. Public JSON/GP/clipboard paths can omit owned data or reject valid legacy shapes; Tasks3/6 test firstFret0/wide/hidden/zero-string snapshots, raw versus effective metadata, every lifetime and v1/v2 compatibility.
3. Diagram strings, sounding offsets and unsafe suggested barres can produce wrong or unusable shapes; Task2/4 independently check literal pitch sets, the Fdim7 open-string counterexample and SMF output.
4. Key changes, slash bass, omissions and stale/manual definitions must not change unrelated music; Tasks2/4 test exact scope, mixed guitar/piano/drum arrangements and skipped manual definitions.
5. Library operations can corrupt stored context or accidentally dirty/change the active score; Tasks5/6 test numeric domains/UUID uniqueness, atomic storage, context-safe recall, restart and document independence.
