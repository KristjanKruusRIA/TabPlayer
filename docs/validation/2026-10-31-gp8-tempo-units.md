# GP8 parity P12: tempo units (2026-10-31)

GP8 row P12 asks for tempo curves, tempo units and a global relative tonality. Beat-position linear and step quarter-note tempos already existed. This slice adds tempo units. The global relative tonality is not built (see Limits), so P12 stays partial.

## Behavior
- **Units.** A tempo point can count a dotted quarter, a half or the other GP units: 1 eighth, 2 quarter, 3 dotted quarter, 4 half, 5 dotted half (the codes a GP file's `<Value>100 3</Value>` uses). `TempoPoint` (`setMeasureSettings`) and `RatioTempoPoint` (`replaceTempoAutomations`) take an optional `unit`; absent means a quarter, so every edit logged before this slice replays as it did and serializes with the same bytes (Rust skips the field when absent).
- **What sounds.** The score still stores and plays quarter notes per minute: `Automation.value` is `bpm * quarters per unit` (100 dotted quarters a minute is 150). The playback plan the native player is built from, the MIDI export, GP5 and MusicXML therefore carry the right sounding tempo with no change to timing. Native playback is still the timing authority.
- **Where the unit lives.** alphaTab has nowhere to keep it, so it rides on the automation object (so the copies the editor makes keep it) and on the automation's JSON object as `tabplayertempounit`, written only for a non-quarter unit. A score that never used units serializes as before.
- **One gesture, one edit.** The measure panel has a unit select per tempo change. Applying the measure is one `setMeasureSettings` edit, undone and redone like any other. The tempo and unit fields are rounded to three decimals for display only (125 quarters shows as 83.333 dotted quarters; the stored and applied value is exact). The unit select has its own row. Choosing a new unit keeps the tempo that plays (80 dotted quarters becomes 120 quarters, and only relabels it, so a non-integer tempo can move by one ulp from the division and multiplication, not exactly; choosing the quarter again sends no `unit` at all.
- **Display.** The measure panel shows each tempo in its own unit. The selection summary in the editor shows the opening tempo as, for example, "100 BPM (Dotted quarter note)" when it is not a quarter. The song tempo field in the song panel is still quarter notes per minute; `setScoreInfo` with the tempo the score already plays keeps the opening unit, any other value sets a quarter tempo.
- **GP round trip.** Export rewrites the master-track tempo values of the generated GPIF to the unit each automation is written in (`100 3`), and import reads the unit back, matched to alphaTab's automations by bar and by order within the bar. A value that disagrees with what alphaTab read is ignored. The unit is read only for a new import and for a project the first edit has marked (the partial-capo marker and `appliesFilePartialCapo` gate, which the controller now also sets for a file holding a unit); a project logged before units replays the file's tempo as quarter notes, as it did. The sounding tempo is the same either way. The tempo is written unrounded and CDATA in score text is skipped when the GPIF is patched.
- **Kept through other edits.** Inserting measures at the start, the legacy single-measure removal of the first bar, excerpt export that starts after a unit tempo, and "Write score tempos" (when a written point lands on a tempo already counted in another unit) keep the unit. Replacing tempos with the same sounding values in a different unit is a real edit, not a no-op.

## Evidence
- **TypeScript, `src/editor/tempo-unit.test.tsx` and `tempo-unit-controller.test.ts` (35 tests).** All five units at several speeds sound as the quarter tempo in the playback plan; one `setMeasureSettings` is one logged edit and survives save, reopen and undo (dropping the edit); a pre-units edit replays as quarter notes and re-reading it never invents a unit; `replaceTempoAutomations` takes units and both validators reject 0, 6, 2.5, "3" and null; the unit survives score copies and the song tempo rule above; MIDI export writes 400000 and 500000 microseconds per quarter for 100 dotted-quarter and 60 half-note tempos, read with an independent byte scan; GP export contains `100 3` and `45 5`, a re-import returns the same unit and sounding tempo, and a unit-free score still writes `120 2`; a foreign GPIF `80 3` imports as unit 3 playing 120; two tempos at one position keep their own units; a title containing `</MasterTrack>` does not stop the units being written; inserted and removed first measures, an excerpt, and the sync conversion keep the unit; the measure panel sends the unit and the kept tempo. Run with the source changes stashed, 18 of the 20 fail; the two that pass are the old-edit replay pins.
- **Rust, `edit_types::tests::tempo_units_roundtrip_validate_and_leave_old_edits_unchanged`.** Old tempo points serialize unchanged, units 1 to 5 round trip in both commands, and 0, 6, -1, 2.5 and "3" are rejected. Without the change the field is an unknown field and the test panics.
- **Suite.** `npx tsc --noEmit` is clean. Full `vitest run --testTimeout=60000`: 4849 passed, 18 skipped, 26 failed, the same 26 as with the change stashed; `cargo test --locked --lib`: 430 passed, 1 unrelated failure (see Limits). `cargo fmt` is clean and `rustfmt --edition 2024` was run on `edit_types.rs`.

## Review
A fresh Opus reviewer, read-only and told to attack it, found no sounding-tempo or old-project defect. It found, and these were fixed: (1) GP read and write paired automations by position, so two tempos at one position collapsed onto the first and export could write the wrong tempo; they are now paired by order within the bar, with a test. (2) "Write score tempos" dropped units and the new unit comparison made a matching score a real edit; points that land on a unit tempo now keep it. (3) The unit change rounded to 1e-6, contradicting "keeps the tempo that plays", and the displayed tempo rounded to 1e-9; both are exact now (only the GP text rounds, to nine decimals, and the reader accepts a 1e-6 difference). (4) A score title containing `</MasterTrack>` silently skipped the unit write; the end tag is now searched after the start tag. (5) The legacy bar-1 removal and the excerpt export built quarter tempos; they carry the unit. (6) Dead helpers were removed. The reviewer's other items are Limits below. The fixes were checked by tests but not reviewed a second time.

Independent review then did not approve a68e2ec and found: the nine-decimal rounding on GP write (170 reimported as 169.9999999995; 1e-10 exported as 0 and failed plan validation), the `<MasterTrack>` search matching inside CDATA, an ungated unit read that changed how pre-units projects replay, long decimals in the panel, and two overclaims in this document. All are fixed in the follow-up commit with tests that fail without each fix (the rounding and display tests, the CDATA titles, the marked and unmarked replay with a real base carrying a unit, the controller marking test). The follow-up is not independently reviewed.

## Limits
- **Global relative tonality is not built.** It needs a document setting in the Rust schema, a shift applied to every instrument key in the plan, MIDI export and the native renderer, and a decision about the backing track (which already has its own semitone processing). That does not fit beside the unit work without touching the audio path, so P12 stays partial and the progress files are untouched.
- **The engraved score still shows the quarter equivalent.** alphaTab draws every tempo marking as a quarter note equals its quarter tempo, so the score and printed pages show 150 for 100 dotted quarters while the measure panel and selection summary show the unit. The tempo label text was not repurposed to carry it.
- **Other formats keep the sounding tempo, not the unit.** GP5 and MusicXML export and MIDI carry quarter-note tempos by definition. For non-zip files (`.gp3` to `.gp5`, and `.gpx`, a BCFZ container) `loadInterchangeScore` returns before the unit read, so alphaTab's own conversion applies: the sounding tempo is right and no unit is kept. `.gp3` to `.gp5` store quarter tempos only. Whether a `.gpx` tempo can name a unit was not checked and reading inside its container was not attempted.
- **Forward-only log.** An edit log that uses `unit` is rejected by an older build (`deny_unknown_fields`); the schema version was not raised. Old logs open in this build.
- **GP unit pairing** relies on alphaTab keeping a bar's tempo automations in file order when it reads and in model order when it writes; a file with unusual duplicates that it reorders keeps quarter notes for the unmatched ones.
- **Layout not measured.** The unit select is on its own row so the German label cannot crowd the 284px inspector, but this was not measured in the real app CSS; jsdom has no layout.
- Not exercised in the running app, on a real output device or in the desktop drivers; the proof is the plan, the MIDI bytes and the GPIF text. The controller no-op check (`tempoState`) now includes the unit but has no direct test.
- Rust `unit: null` deserializes as absent, while the TypeScript validators reject it; the app never sends it.
- Worktree results: the TypeScript suite has 26 failures that read GP files from `.analysis/compatibility` or the sound bank, which this worktree lacks, and match the failures with the change stashed. In the Rust suite `file_library::index::tests::a_page_search_over_fifty_thousand_rows_stays_fast` fails under load; it is unrelated.
