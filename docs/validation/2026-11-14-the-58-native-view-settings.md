# THE-58: native view settings and the keyboard panel per document (U14, U15)

Date: 2026-11-14. Branch `agy/the-58-native-view-settings`. Closes three of the open remainders of [2026-11-13-the-58-instrument-views.md](2026-11-13-the-58-instrument-views.md). The tracker rows stay partial for the reasons under Limits.

## Built

### The person's instrument view options are kept natively

- **Where.** `app-settings.json` in the app's config directory (the same folder, and the same desktop-test isolation through `TABPLAYER_TEST_APP_DATA_DIR`, as the saved tunings). Code: `src-tauri/src/app_settings.rs`, commands `app_settings_read` and `app_settings_put_instrument_view` in `src-tauri/src/lib.rs`. This replaced the earlier tuning-only name of the folder helper (`personal_data_directory`); behaviour of the tuning, harmony and style libraries is unchanged.
- **Format.** `{"format":"tabplayer-settings","version":1,"instrumentView":{leftHanded,noteNames,neck,expanded,focus}}`. Options kept: left-handed neck, note names, neck choice, size, Show focus. Click to edit keeps its own older browser key, as before.
- **Reading is untrusted.** At most 64 KiB are read (a larger file is not held in memory), and the bytes that were read are the bytes that are parsed (no check of the file followed by a later read). Each field is checked on its own against its allowed values; a bad field takes its default and the others are kept. Unknown fields are ignored and kept when the file is next written. Nothing in the file names a path. A file that is not JSON, not an object, not this format, a newer version, or too large is renamed to `app-settings.json.unreadable` (replacing an earlier one) and the defaults apply; it is never deleted and never crashes the app. A section that is absent counts as "nothing stored yet".
- **Writing.** The front end sends the whole record; the native side validates it strictly (enums, no unknown fields), compares it with what is stored, and writes nothing when it is the same. Otherwise the file is written with the existing atomic writer (`files::write_bytes`: temporary file then replace) under a lock.
- **Browser copy.** `localStorage` stays as a read-through cache for the first paint (the views start synchronously from it). The app reads the native settings once after start (`syncInstrumentViewPreferencesFromNative`, called from `App`); a native record wins, and views that are already open follow it. A choice made before the native read arrives is kept and merged over the native record, so a stale browser copy never overwrites a native choice. If the native settings cannot be read, nothing is sent natively that session.
- **Migration.** With no native record yet, the existing browser record (and the older handedness key) is repaired field by field, sent natively once and written back repaired; a hostile or damaged record gives the defaults, never more. After that the native record is the authority and the browser copy is refilled from it, which is what survives a WebView profile reset.
- **View mode (U15).** Not persisted, on purpose, and left as it was: the mode is a choice about one track (Drums on a guitar track, or Neck + keys on a drum staff, mean nothing there) and Auto follows the track, as the code comment in `InstrumentView.tsx` and the 2026-11-13 note say. Only the neck a guitar or bass choice picked is kept.

### The keyboard panel is part of the document view

- `DocumentViewState` (`src-tauri/src/recovery.rs`, `src/workspace/types.ts`) has a new `keyboardVisible`, added the way `scoreDisplay` was: absent when hidden (`#[serde(default, skip_serializing_if)]`), so a view that never showed the keyboard serializes byte for byte as before, and an old view reads as hidden. It rides the existing view path (`workspace_set_view` into the recovery checkpoint), so it is never an edit: no history entry, no revision, no modified mark. It is kept with a sealed (password-locked) document's display preferences, like zoom and the instrument panel.
- The front end never holds both panels: a view with both repairs to the instrument panel.
- **Where view state lives.** Only in the recovery checkpoint of the session, not in `.tabplayer` projects. A `.tabplayer` file and its edit log did not change, so old projects open and replay as before.
- **Older builds.** Like `scoreDisplay`, `DocumentViewState` rejects unknown fields, so a build older than this one cannot read a recovery checkpoint written while the keyboard panel was shown (it reports the view as damaged and resets only that view; music and history are kept). Checkpoints written with the panel hidden are unchanged.

## Limits

- Native settings are read once at start and written on every change, but are not pushed to other open views of the app; the app has one window, so "the same across windows" was not exercised.
- A failed native write is silent: the choice still applies and the browser copy keeps it, and the next start sends nothing over a native record it cannot read.
- The keyboard panel is remembered only where view state is (the session's recovery checkpoint), not in the `.tabplayer` file; a document opened from disk starts on its own view.
- A recovery checkpoint written with the keyboard panel shown cannot be read by a build older than this one (see above).
- Not verified: the concurrent-launch case of two app instances writing the settings file; the corrupt-settings path in the running app (covered by Rust tests only); et and de text did not change.
- Overlays on the main instrument view, the scale workflow, one neck only and the original-GP8 comparison remain as in the 2026-11-13 note.

## Toolbar defect found by `instruments.mjs`

Commit 21becae (THE-57) put the Key group in the transport row, which grew from about 840 to 1003px, but the toolbar breakpoints in `src/workstation/gp-shell.css` (transport on its own row below 1340px; display controls on a second row below 1880px) were not moved. The centred transport then overflows its track and its right end lay under the view buttons: Original key from about 1330 to 1390px wide, More playback from 1400 to 1450px, and again Original key and More playback from 1880 to about 1990px. At 1440px (the driver's window) the centre of More playback was covered, so a person could not click it either. Not dependent on the instrument panel or the key value. Fix: the breakpoints are now 1500px and 2040px (`gp-shell.css:115-121`), pinned in `src/shell/small-window.css.test.ts`; `parity-key-shift.mjs` now asserts that no transport control is under another element at 1920, 1440, 1366, 1280, 1101 and 960 wide (red at 1920 before the fix). Effect: at 1880 to 2039px wide the display controls now take a second row, as they do below 1880.

## Review fixes (2026-11-14, second round)

### Settings file (`src-tauri/src/app_settings.rs`)

- **Newer version.** A file whose `version` is above 1 is never changed: reading gives defaults with `readOnly: true`, and a put is refused with `settings-newer-version`. The front end shows one translated status (`instruments.settings_newer`) on the first change and sends nothing more.
- **Setting aside.** Only a file that was read and is not valid settings (not JSON, not an object, other format, version 0 or not a number, over 64 KiB) is set aside. A read or open error is returned as an error and never sets anything aside. Kept copies are numbered `app-settings.json.unreadable-1` (newest) to `-3`; at most 3 are kept, the oldest is pruned, and no kept copy is overwritten except that pruned one. If a copy cannot be kept (a directory or a failed rename on the name), it is reported once on stderr, the defaults apply in memory, and later reads and puts work.
- **Unknown fields** are kept inside `instrumentView` as well as at the top level (the test asserts `extra` survives).
- **Size cap on write.** The file is written pretty; if that passes 64 KiB it is written compact; if that still passes, the write is refused (`settings-too-large`) and the old file stays byte for byte.
- **Other edge cases.** The file is opened without blocking (non-blocking flag on Unix) and its type is taken from the open handle, so a pipe or device at the path is an error and cannot hold the lock; a poisoned lock is recovered; reading never writes a defaults file, and the front end sends nothing at a first start when nothing was chosen. The Unix non-blocking open is code that was not compiled or run here (Windows only).
- Tests that could not fail were replaced: the directory case now asserts the error, no aside copy and the directory left; the blocked-aside case, the cap, the newer version, the numbered copies and the poisoned lock each assert their result.

### Front end (`src/instruments/view-preferences.ts`)

- **Unsent marker.** While a choice has not reached the native settings (a failed write, or a failed read), the browser copy carries `tabplayer.instrumentView.unsent`. The next start sends the browser copy over the older native record instead of the other way round, and clears the marker once the write succeeded. Without the marker the native record wins as before.
- **One quiet status**, in en, et and de (`instruments.settings_not_saved`, `instruments.settings_newer`), shown in the instrument view when the options could not be saved, until a save succeeds. A failed native read also tells the person, keeps the choices, and the next choice tries the read again.
- **Saving no longer depends on the browser store.** After the native read the whole record is kept in memory and every change is sent from it; a choice made before the read is remembered in memory and merged over the native record, not read back from storage. With storage refusing, the native settings are still written.

### Toolbar layout (`src/workstation/gp-shell.css`, `src/shell/toolbar-fit.ts`, `src/Transport.tsx`)

The earlier fix moved the breakpoints up to widths that were tuned by hand and gave a maximised 1920px window a second toolbar row. They are now derived from measurements.

- **Method.** A sweep in steps of 5px through 1400 to 2300 (and 1100 to 2560 for the first pass), in English, Estonian and German, with a selection present (so the 34px loop-selection button is in the row), looking at the centre of every control of every toolbar group (edit and view buttons, display controls, transport, practice and the rest) for another toolbar element on top of it. The sweeps were run on the built app with the candidate layouts forced by an injected style sheet, with the Key group in the row and with it hidden.
- **Content widths** (CSS px, at 2400 wide, where nothing is squeezed): left group 265, right group 195, Key group 133 (inside a transport of 1003, 1038 with a selection); the display group 524 in English, 626 in Estonian and 720 in German. Only the display group differs by language.
- **Measured first clean widths** (with a selection): two-row layout with the Key group in the row clean from 1495 in all three languages. Single row with the Key group folded: English 1900, Estonian 2005, German 2095. Single row with the Key group in the row: English 2035, Estonian 2135, German 2230. Every threshold is the measured width plus 20px and rounded up to 5.
- **Rule.** Transport on its own row below 1515; display on a second row below 1920 (English), 2025 (Estonian) and 2115 (German), by language through `:lang()` on the app shell (the shell now carries `lang`); inside the single row the Key group is in More playback until 2055 (English), 2155 (Estonian) and 2250 (German); in a window of 1100px or less it is folded as before. `src/shell/toolbar-fit.ts` holds the measurements and derives the numbers; `src/shell/small-window.css.test.ts` ties the style sheet and the Key fold to them, and `Transport` takes its media query from the same table.
- **Result.** At 1920 wide English has one toolbar row, with the Key group in More playback. Estonian and German do not: before the Key group existed, their single row already overlapped (the transport painted over Speed, More playback and the view buttons up to about 1960 and 2055 wide), so at 1920 they use the second row for the display group, as they must. That is a pre-existing limit of those languages, not new.
- **Known limit.** German below 1200px wide overlaps inside the display group (Actual zoom under the fit controls) even with the Key group folded; it is not the Key group's and is not asserted below 1200. The measured edges are from steps of 5px, with the margin above; a width between steps was not measured. The sweep found English with the Key group in the row bad at 2020 to 2030 but clean at 1900 to 2015, which is not monotonic; the threshold takes the highest bad width.
- **Checks.** `parity-key-shift.mjs` now checks every toolbar group, not only the transport, at 960, 1101, 1280, 1366, 1440, 1536, 1600, 1920 and 2560 and at each breakpoint minus one, at and plus one, in en, et and de (the language is set the way the app keeps it, in the browser storage, then the page is reloaded), and asserts where the Key group is.
