# THE-208 and THE-209: edit-target box after a resize, and the Library metadata alert (2026-11-13)

## THE-208: the edit-target box stays put when the window is widened

### Cause

`ScoreView` places everything drawn over the score (the edit-target box, selection marks, error shading, loop bands, scale diagrams, bar handles) from the canvas offset: `offset()` reads `uiFacade.getOffset(null, canvasElement)` and `mapped()` adds it to each alphaTab bounds box (`src/ScoreView.tsx`). `.score-live-paper` is centred in the score area (`margin-inline:auto`, `src/ScoreView.css`), so a resize of the window, or a panel opening beside the score, moves the page and changes that offset without alphaTab drawing the score again.

`refreshCaret` ran only after a render (`postRenderFinished`), when the target, the score, the zoom, the layout or the projection changed. The score area's measured size (`available`) was not among its triggers. When the page moved without a new render, the box kept the position computed for the old offset.

Reproduced on the unfixed desktop build: at 1280x800 the box held the first beat; after 960x600 and then 1600x1000 the box (x 392.6 to 419.3) sat left of the first beat (cursor at x 506.9).

### Fix

`src/ScoreView.tsx`:

- One layout effect, keyed on `available.width` only, runs `refreshOverlays()` (selection marks, edit-target box, error shading, loop bands, scale diagrams, bar handles). It does nothing in paged layouts (`presentation.current.physical`), whose marks come from the arrangement and are refreshed when it is rebuilt. While a render is under way each refresh stands down, as before, and the render's own finish places the marks.
- Height is not a key: in a live layout the page is centred horizontally only. Checked in the real window by resizing to the same width with another height (1440x900 to 1440x600 to 1440x1000) and by hiding the bottom dock; the box stayed put.
- `refreshOverlays()` reads the canvas offset once per pass (`passOffset`), not once per box, and replaces the six-call lists after a render and after a paged arrangement change. The duplicate `available` keys on the bar-design effect are gone.
- A note-entry preview is cleared when the page moves (it returns with the next mouse move). An open symbol popover closes when the live page has moved more than 1 px from where it stood once the popover had been laid out and settled (two animation frames after it opens). The baseline is taken late on purpose: in a score area shorter than the popover it overflows, a vertical scrollbar appears and the centred page shifts about 8 px as it opens, and a baseline taken at open closed the popover at once. A real resize in the first two frames is not seen by this rule. The existing 24 px rule alone left it up to 12 px off its symbol after a smaller resize. This was real, not only suspected. In paged layouts the popover still uses the 24 px rule only.
- The last pass's cost is kept as the user-timing measure `tabplayer:overlay-refresh` (one entry, replaced each pass).

### Cost of one refresh

Measured in the real app (`performance.getEntriesByName('tabplayer:overlay-refresh')`), parchment layout:

- Windowline (8 bars): 0.1 to 10 ms per pass over the driver's resizes, mostly 4 to 8 ms.
- A generated 200-bar, four-track guitar score (70 rendered chunks), resized across 1000 to 1600 px: 3.1 and 3.3 ms for a resize that only moved the page, and 102, 106 and 179 ms for resizes where the score was also laid out again and the pass ran after that render. The post-render pass existed before this change; it is not new cost, but it is the larger figure on a big score and was not reduced here.
- The 100-bar four-track fixture was not available in the worktree, so the generated score stands in for it.

### Tests

- Vitest, all failing before the effect existed (they fail with the effect keyed on nothing) and passing now:
  - `ScoreView.test.tsx`: the edit target on two resizes (expected 235px, got 35px before), and the range handle, scale diagram and edit target together.
  - `ScoreView.layouts.test.tsx`: loop bands, selection bands and error shading in a live layout, with no render in between.
  - `ScoreView.bar-design.test.tsx`: the bar width handles.
  - `ScoreView.symbols.test.tsx`: the popover closes on a 10 px page move once settled, and stays open when the scrollbar it brings shifts the page by 8 px as it opens (the second test failed against the open-time baseline).
- Not covered by a unit test: the note-entry preview clearing. It needs a hit test the fake renderer cannot give. It is one `setGhost` call in the same effect and was not looked at in the real window.
- `tests/desktop/parity-edit-target-resize.mjs` now measures on the first frame after each change as well as settled (a one-frame lag fails), keeps the box's place on the page constant through each resize (a different page width compares only with the same width), checks the second beat as well as the first, adds height-only and odd-width sizes, and toggles the Bottom dock as well as the Inspector. The first frame is judged by the box's place on the page (the cursor line is alphaTab's own and once trailed the box by 1.6 px on the first frame, so it is the oracle once settled). It also opens the symbol popover on the score title at 960x600 and 1280x800 and checks it is still open after about a second. 37 placements; two runs in a row passed.

## THE-209: Library metadata alert after opening a score

### Answer

It is neither a stale callback nor a failed record of an ordinary score.

- Opening a score the person chose from the Library (Recent or a folder), by the Open dialog, a drop or a launch file records a receipt, and the page's metadata callback finds it. No alert. Checked in the real app: opening a copy of the example from outside the app's folders, twice, shows no alert, so a second open of the same file is not the cause either.
- The alert appears only for a score file that lives inside the app's own protected storage (the bundled `library` folder, the Library catalog or the recovery folder). `FileLibrary::record_success` refuses to record such a path (`protected.check`), by design, so no receipt exists. The page then still sends the score's title, artist and track names (`WorkspaceLibrary.acknowledge`, since the open used `metadata=true`), and `metadata_ack` refused it with "Metadata requires the exact successful file operation for this document revision." (`src-tauri/src/file_library/service.rs`, in `metadata_ack`).
- The test route hits it because `TABPLAYER_TEST_OPEN` pointed at `.analysis/desktop-smoke/library/examples/example-windowline.tabplayer`, which is inside the test app's bundled `library` folder. An ordinary user reaches it only by opening a file by path from inside the install folder. Examples chosen in the Library (`LibrarySource::Example`) open without metadata and never ask for it.
- 7f298b8 (receipt kept when another tab closes) was a different defect. It is unchanged and still holds.

### Fix

`metadata_ack` keeps the receipt lookup first. Only in its not-found arm does it return the unchanged catalog, and only when `ProtectedPaths::is_protected` answers `Ok(true)` for the receipt's path. `is_protected` is new: `check` is now `is_protected` plus the refusal, so every other caller behaves as before. A check that cannot tell (an unreachable volume, an unresolved `..`, a dangling alias) is an error, not "protected", and keeps the old refusal. Paths that have a receipt behave exactly as before, including the sealed branch, which still strips Recent details and scrubs the folder index.

A first version of this fix returned early on any `check` error and before the sealed branch. Review found that it failed open on a non-protected path whose check errors (for example a protected score on a drive that drops before the page's callback would no longer have its old plain details stripped). That is corrected as above.

### Tests

- `a_score_opened_from_the_bundled_folder_is_never_recorded_and_its_details_are_not_an_error`: failed with the exact alert text before the fix.
- `a_score_without_a_receipt_whose_path_cannot_be_checked_is_still_refused` (a dangling alias): failed against the first version of the fix (it returned Ok), passes now.
- `a_score_without_a_receipt_outside_protected_storage_is_still_refused`, `a_score_opened_through_an_alias_of_the_bundled_folder_is_let_go_quietly` (a junction or symlink to the bundled folder), and `protected::tests::says_protected_only_when_it_can_tell` (`Ok(true)`, `Ok(false)` and an error for an unresolved `..`).
- The sealed-score cases (a receipt, old plain details, stripped and scrubbed) are the existing sealed-score tests in `service_tests.rs`; the receipt branch is untouched. A sealed score inside protected storage with no receipt cannot be set up in a unit test (saving there is refused) and was not tested.
- Real app, unfixed build: the example opened by `TABPLAYER_TEST_OPEN` showed the alert; a copy outside the app folders showed none. Fixed build: no alert for either, two Open presses each.

### Stated limit

If a user adds a Library folder that contains the app's bundled `library` folder, scores inside the bundled part are protected, are never recorded in Recent, and give no message when opened. This is unchanged by the fix and was not tried in the real app.
